== 1. Document Request (Network) ==

I opened the project using Live Server and, in the "Network" tab of the DevTools, reloaded the page to see what the browser was requesting. The first request that appears is for the document itself, from which I gathered the following details:

Full URL: http://127.0.0.1:5500/index.html
Protocol:    http
Host:         127.0.0.1 (this is my own computer, which is why it’s not a domain name)
Port:         5500 (the default port used by Live Server)
Path:         /index.html
Method:       GET
Status Code:  200 OK

A 200 status code means the server found the page and sent it to me without any issues. I then manually entered a path that doesn't exist to see what would happen:

Non-existent path: http://127.0.0.1:5500/promociones.html
Status Code:       404 Not Found

In this case, the server responds, but it indicates that it does not have that file. This helped me understand that a 404 error doesn't mean the server is down; rather, it means that the requested resource does not exist.

== 2. Roles of HTML, CSS, and JavaScript ==

I used the "Rueda Libre" project to illustrate these concepts, moving beyond simple definitions:

HTML represents the structure and content—for example, a price table, including its rows, columns, and the information contained within them.
CSS defines the visual appearance—for instance, the brand's color scheme or ensuring the menu is displayed horizontally rather than as a vertical list.
JavaScript handles behavior—such as validating a reservation form before it is submitted and alerting the user if any information is missing.

If I remove the CSS, the page retains all its content, though it appears plain. If I remove the HTML, nothing remains. This was the simplest way I found to distinguish between them. == 3. Relative Path Table ==

For this table, what helped me was to always consider the location of the file where I am writing the link. == 4. Region Layout (Mini-Challenge 5) ==

Before touching the code, I created a layout for each page to determine which region should be nested within another. Here is the final structure:

index.html:    header (h1 + nav) > main (4 sections; the "Our Services" section contains 3 `article` elements) > footer
tarifas.html:  header (logo + name + nav) > main (h1, a section for rates, a section with the ID `#recorridos`, and an information section containing an `aside` for "What to bring") > footer
reservas.html: header (logo + name + nav) > main (h1, an `aside` for operating hours) > footer

I did not use any `div` or `span` elements. Each part uses a semantic tag that describes its purpose: the services are marked as `article` elements because each one is self-contained, while the "What to bring" section and the operating hours are marked as `aside` elements because they serve as supplementary information rather than the page's primary content.

== 5. Justification of Form Controls (Mini-Challenge 6) ==

For the reservation form, I did not choose the controls at random; rather, I selected them based on the nature of the user's input:

Bicycle type -> `radio` buttons. There are 3 options, and only one can be selected. Using `radio` buttons allows all options to be visible simultaneously, enabling the user to compare them without needing to open a menu.
Plan or route -> `select` (dropdown). This is a closed list with multiple options; a dropdown menu is more space-efficient.
Policies -> `checkbox`. This represents a simple binary decision: accept or decline.

== 13. v1.0 Release (Mini-Challenge 12) ==

For version 1.0, I made the following changes:

- "New" label: The `.card` element is set to `position: relative`, and the `.label` element to `position: absolute` with `top` and `right` properties. This ensures the label is positioned relative to its card rather than the entire page.
- WhatsApp button: Set to `position: fixed` in the bottom-right corner so it remains in place while scrolling. I added `padding-bottom` to the `body` to prevent the button from obscuring the footer.
- Organized `styles.css` into logical blocks: variables, base, navigation, components, and form. Removed any duplicate CSS rules.
- Final review: 0 "404" errors in the Network tab, no inline styles, and the focus state is clearly visible when navigating via the Tab key across all 3 pages.

MR1 to MR4 (v0.1): Created the repository, the homepage, the pricing section (using tables), the booking page, and the menu.
MR5 to MR8 (v0.2): Implemented semantic HTML tags, built the form with native validation, conducted an accessibility audit, and reviewed the color palette.

Instead of guessing why something doesn't look the way it should, I can now investigate and find the cause.
