== 1. Petición del documento (Network) ==

Abrí el proyecto con Live Server y en DevTools, pestaña Network, recargué la página para ver qué pedía el navegador. La primera petición que aparece es la del documento, y de ahí saqué estos datos:

URL completa: http://127.0.0.1:5500/index.html
Protocolo:    http
Host:         127.0.0.1 (es mi propio computador, por eso no es un dominio)
Puerto:       5500 (el que usa Live Server por defecto)
Ruta:         /index.html
Método:       GET
Código:       200 OK

El 200 quiere decir que el servidor encontró la página y me la envió sin problema. Después escribí a mano una ruta que no existe para ver qué pasaba:

Ruta inexistente: http://127.0.0.1:5500/promociones.html
Código:           404 Not Found

Ahí el servidor responde, pero dice que ese archivo no lo tiene. Me sirvió para entender que el 404 no es que el servidor esté caído, sino que lo que pedí no está.

== 2. Roles de HTML, CSS y JavaScript ==

Lo pensé con el mismo proyecto de Rueda Libre para no quedarme solo en la definición:

HTML es la estructura y el contenido. Por ejemplo, la tabla de tarifas: qué filas y columnas hay y qué dice cada una.
CSS es cómo se ve. Por ejemplo, los colores de la marca y que el menú quede horizontal en vez de una lista hacia abajo.
JavaScript es el comportamiento. Por ejemplo, revisar el formulario de reservas antes de enviarlo y avisar si falta algo.

Si quito el CSS la página sigue teniendo todo el contenido, solo que se ve plana. Si quito el HTML no queda nada. Esa fue la forma más fácil que encontré de diferenciarlos.

Para esta tabla lo que me sirvió fue pensar siempre desde dónde está el archivo en el que escribo el enlace. Si estoy dentro de la carpeta paginas y quiero ir a index.html, tengo que salir una carpeta, y eso es el ../ . Si los dos archivos están en la misma carpeta, basta con el nombre.

El último caso es el del logo. Desde tarifas.html tengo que salir de paginas y luego entrar a img. Si se me olvida el ../ la imagen no carga, y en Network se ve como un 404, así que es fácil detectar el error.

== 4. Esquema de regiones (MiniReto 5) ==

Antes de tocar el código hice el esquema de cada página para ver qué región iba dentro de cuál. Quedó así:

index.html:    header (h1 + nav) > main (4 section; la de "Nuestros servicios" tiene 3 article) > footer
tarifas.html:  header (logo + nombre + nav) > main (h1, section de tarifas, section #recorridos, section de información con un aside "Qué llevar") > footer
reservas.html: header (logo + nombre + nav) > main (h1, aside con el horario) > footer

No usé ningún div ni span. Cada parte tiene una etiqueta semántica que dice lo que es: los servicios son article porque cada uno se entiende solo, y "Qué llevar" y el horario son aside porque son información de apoyo, no el contenido principal de la página.

== 5. Justificación de controles (MiniReto 6) ==

Para el formulario de reservas no escogí los controles al azar, sino según cómo responde la persona:

Tipo de bicicleta -> radio. Son 3 opciones y solo se puede escoger una. Con radio se ven todas al mismo tiempo y la persona compara sin abrir nada.
Plan o recorrido  -> select. Es una lista cerrada con más opciones, y en un desplegable ocupa mucho menos espacio.
Políticas         -> checkbox. Es una sola decisión de sí o no: acepto o no acepto.

== 7. Auditoría de accesibilidad (MiniReto 8) ==

Primero revisé lo básico y estaba bien: lang="es" en las 3 páginas, un solo h1 por página sin saltar niveles de títulos, alt en las fotos y se puede recorrer todo con el teclado.

Después busqué cosas que se pudieran mejorar. Encontré seis:

1. El enlace "mira cómo llegar" no se entiende si se lee solo (un lector de pantalla puede listar los enlaces sin el texto de alrededor). Lo cambié por "cómo llegar a nuestra sede".
2. El enlace al mapa abría otra pestaña sin avisar. Le agregué "(se abre en otra pestaña)".
3. El logo del header tenía un alt que repetía el nombre del negocio, que ya está escrito al lado. Le dejé alt="" porque ahí es decorativo y si no el lector lo dice dos veces.
4. "Reservar ahora" estaba repetido sin contexto. Ahora uno dice "Reservar ahora tu bicicleta" y el otro "Reservar un recorrido guiado".
5. El formato del documento, del celular y el rango de fechas solo estaba en el title, que no se ve a menos que pases el mouse. Lo puse como texto de ayuda visible con <small>.
6. El menú no indicaba en qué página estás. Le agregué aria-current="page" al enlace de la página actual.

== 8. Contraste de la paleta (WCAG) ==

Revisé cada combinación de colores de la marca con un verificador de contraste. Para texto normal se necesita mínimo 4.5:1.

Combinación             | Ratio   | Clasificación
Blanco / Verde Ruta     | 5.31:1  | Apta texto normal
Blanco / Naranja Pedal  | 2.22:1  | No apta
Azul Noche / Naranja    | 7.20:1  | Apta texto normal
Azul Noche / Crema      | 14.83:1 | Apta texto normal
Gris Asfalto / Crema    | 5.57:1  | Apta texto normal
Verde Ruta / Crema      | 4.93:1  | Apta texto normal
Naranja Pedal / Crema   | 2.06:1  | No apta
Blanco / Azul Noche     | 15.97:1 | Apta texto normal

Lo que más me sorprendió fue el naranja: es el color más llamativo de la marca, pero con blanco o sobre crema no se lee bien. Por eso lo uso solo como fondo, con texto Azul Noche encima.

Con eso armé el mapa de uso de color:
- Fondo general: Crema. Textos y títulos: Azul Noche. Texto secundario: Gris Asfalto.
- Enlaces: Verde Ruta. Botón principal: fondo Verde Ruta con texto blanco.
- Botón secundario y destacados: fondo Naranja Pedal con texto Azul Noche (nunca blanco).
- Header y footer: fondo Azul Noche con texto blanco.
- El naranja nunca va como color de texto sobre crema.

== 10. Herencia (MiniReto 9) ==

Para comprobar la herencia seleccioné un <p> y miré la pestaña Computed en DevTools.

Lo que sí se hereda: font-family. El <p> muestra "Open Sans" aunque esa fuente solo la declaré en el body. El párrafo la toma del padre sin que yo se la ponga.

Lo que no se hereda: background-color. El <p> muestra rgba(0,0,0,0), o sea transparente. Se ve crema, pero no porque tenga ese color, sino porque deja ver el fondo del body que está detrás. Esto me pareció curioso porque a simple vista uno pensaría que sí lo heredó.

== 11. Conflicto de especificidad (MiniReto 10) ==

Le puse la clase .activo al enlace de la página actual para pintarlo distinto, pero el color no cambiaba. Revisando en DevTools vi que el color de .activo aparecía tachado, y era por esto:

#menu a  -> (1,0,1)  un id y un elemento
.activo  -> (0,1,0)  una clase

Gana #menu a porque tiene un id, y un id pesa más que cualquier cantidad de clases. La solución fue escribir el selector #menu a.activo, que da (1,1,1) y le gana al otro. No usé !important, porque eso arregla el problema en el momento pero después complica cualquier cambio.

También revisé el contraste de los estados del menú: gris sobre blanco 6.0:1, verde sobre blanco 5.31:1, hover azul sobre blanco 15.97:1 y el botón blanco sobre verde 5.31:1. Todos pasan.

Tuve que hacer un ajuste al mapa de color: el header pasó a tener fondo blanco, porque el gris sobre Azul Noche solo daba 2.66:1 y no se leía bien.

== 12. Medición de tarjeta (MiniReto 11) ==

Medí la tarjeta en una ventana de 1280 px. La tarjeta tiene width:100% (el main mide 960 px), padding de 1.5rem (24 px por lado) y borde de 1 px.

content-box: 1010 px de ancho total. El width se aplica solo al contenido (960), y encima se suman 48 de padding y 2 de borde. Por eso la tarjeta se sale del main.
border-box:  960 px de ancho total. El padding y el borde quedan por dentro del width, así que el contenido se reduce a 910 px y la tarjeta cabe exacta en el main.

Por eso dejé box-sizing: border-box para todo el sitio: así el ancho que escribo es el ancho que se ve.
